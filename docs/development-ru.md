# Руководство по разработке

## Структура и область применения

`include/` содержит общие заголовки API и заголовочный (header-only) парсер командной строки.
`src/` содержит переиспользуемые реализации алгоритмов, `main.c` для диспетчеризации CLI и `benchmarks.c` для экспериментов по замерам времени. `tests/` не зависит от точки входа CLI и компонуется с теми же объектами алгоритмов, что и приложение.

Автономные программы находятся в `examples/`. Отобранный список из 19 завершающихся программ доступен через `mk/examples.mk`. Исторические небезопасные и анимированные эксперименты остаются исключёнными. Каталог примеров отражает это различие. Запускайте из корня:

```sh
make run-example EXAMPLE=kmp
make test-examples
make demo
```

Статьи `docs/article*.md` сохраняются как справочный материал, а не как спецификация или гарантия корректности.

## Конфигурация сборки

Требуются GNU Make, GCC или Clang с C11 и поддержкой `__uint128_t`, POSIX-окружение и libm. Целевая платформа CI — Linux; Windows сейчас не тестируется. Python 3 нужен для тестов CLI, Doxygen — для HTML-документации. Сторонний фреймворк для тестов не требуется.

Корневой Makefile передаёт настройку, сборку, тесты и документацию в `mk/config.mk`, `mk/build.mk`, `mk/test.mk` и `mk/docs.mk` соответственно. `mk/examples.mk` отвечает за явный список разрешённых примеров и цели демонстрации. Все поддерживаемые примеры компонуются с общими объектами алгоритмов так же, как C-тесты; отдельный список зависимостей для каждого примера не нужен. Библиотеки указываются в `LDLIBS`, параметры компоновщика — в `LDFLAGS`, параметры препроцессора — в `CPPFLAGS`. Зависимости заголовков генерируются автоматически (`-MMD -MP`).

```sh
make -j2
make run ARGS="--help"
make DEBUG=1 test                 # bin/debug и build/debug
make sanitize                    # bin/sanitize и build/sanitize
make CC=clang BUILD_DIR=build/clang BIN_DIR=bin/clang test
make docs                        # build/docs/html/index.html
```

Сборки release, debug и sanitizer изолированы. При смене компилятора или пользовательских флагов используйте отдельные `BUILD_DIR` и `BIN_DIR` либо сначала выполните `make clean`: Make не обнаруживает произвольные изменения флагов компилятора. `make clean` удаляет сгенерированные каталоги `build/` и `bin/`, включая локальную документацию.

## Тесты

- `test_algorithms.c`: детерминированные граничные тесты, известные векторы хешей/Фибоначчи и 10 000 проверок свойств для обратных преобразований Мортона/Грея, квадратного корня, деления, случайных диапазонов и битовых операций.
- `test_strings.c`: примеры расстояния редактирования, обратные преобразования сжатия, длинные серии RLE, некорректные и переполняющиеся счётчики RLE.
- `test_cli.py`: интеграционные проверки через подпроцессы для справки, ошибок парсера, валидации экспоненты и успешных вычислений.
- `test_parser.c`: грамматика парсера, повторяющиеся опции, отсутствующие аргументы, валидация таблицы опций и границы строгого числового преобразования.
- `make test-examples`: каждый поддерживаемый пример запускается в подпроцессе с тайм-аутом.
- `make demo`: детерминированные сценарии с проверкой вывода из `demos/tour.py`.
- `make sanitize`: те же тесты с AddressSanitizer и UndefinedBehaviorSanitizer.

Проверки остаются активными при `NDEBUG`. Тесты не измеряют производительность и не запускают полный набор бенчмарков. Для новых тестов алгоритмов добавляйте файлы `tests/test_*.c`; Make обнаруживает их автоматически. CI запускает обычные тесты и тесты с санитайзерами как с GCC, так и с Clang. CI также собирает и выполняет дымовые тесты отобранных примеров и запускает тур; небезопасные исторические эксперименты намеренно исключены.

## Добавление алгоритма или трюка

Держите алгоритм независимым от ввода-вывода. Переиспользуйте существующий модуль, если тема подходит; иначе добавьте `include/<name>.h` и `src/<name>.c`. Make обнаруживает `src/*.c` автоматически. Не добавляйте ещё один реестр и не копируйте реализацию в тесты, примеры или бенчмарки. Опция CLI необязательна: пример — простейший способ запустить эксперимент, не расширяя `src/main.c`.

### 1. Определите контракт и реализуйте

Документируйте в публичном заголовке диапазоны входных значений, поведение при нуле/переполнении, владение, погрешность приближения и платформенные предположения. Для битовых трюков предпочитайте беззнаковые целые фиксированной ширины. Избегайте знакового переполнения, сдвигов за пределами разрядности и type-punning указателей; для битовых представлений используйте `memcpy`. Явно указывайте предусловия, а не полагайтесь молча на неопределённое поведение.

Например, новый `include/bit_count.h` мог бы содержать:

```c
#ifndef BIT_COUNT_H
#define BIT_COUNT_H
#include <stdint.h>

/** Подсчитать установленные биты в любом значении uint32_t, включая ноль. */
unsigned bit_count(uint32_t value);
#endif
```

С `src/bit_count.c`:

```c
#include "bit_count.h"

unsigned bit_count(uint32_t value) {
    unsigned count = 0;
    while (value) {
        value &= value - 1;
        ++count;
    }
    return count;
}
```

Эти фрагменты — рецепт, а не дополнительный устанавливаемый API. Используйте описательное имя для вашего реального алгоритма, сохраняйте сведения об авторстве и объясняйте, почему трюк работает. Держите простую эталонную реализацию в тестах, а не в рабочем коде.

### 2. Добавьте детерминированный тест

Создайте `tests/test_bit_count.c`; все файлы `tests/test_*.c` обнаруживаются и компонуются с общей реализацией автоматически. Используйте `CHECK` из `check.h`, а не `assert` (который исчезает при `NDEBUG`). Каждый тестовый файл имеет собственный `main`:

```c
#include "bit_count.h"
#include "check.h"

static unsigned reference(uint32_t value) {
    unsigned count = 0;
    for (unsigned bit = 0; bit < 32; ++bit) {
        count += (value >> bit) & 1u;
    }
    return count;
}

int main(void) {
    CHECK(bit_count(0) == 0);
    CHECK(bit_count(UINT32_MAX) == 32);
    for (unsigned bit = 0; bit < 32; ++bit) {
        CHECK(bit_count(UINT32_C(1) << bit) == 1);
    }
    uint32_t state = 1; /* Фиксированное зерно: сбои воспроизводимы. */
    for (unsigned i = 0; i < 10000; ++i) {
        state = state * UINT32_C(1664525) + UINT32_C(1013904223);
        CHECK(bit_count(state) == reference(state));
        CHECK(bit_count(state) + bit_count(~state) == 32);
    }
    return EXIT_SUCCESS;
}
```

Сначала покройте известные ответы и границы, затем сравнивайте с независимой эталонной реализацией и проверяйте свойства (обратные преобразования, инварианты, монотонность, где применимо). Проверяйте недопустимые входные данные только когда API определяет их поведение. Для плавающей запятой задавайте абсолютные/относительные допуски и тестируйте документированную область, включая неконечные значения, если они поддерживаются. Не используйте замеры времени как утверждения.

```sh
make list-tests
make run-test TEST=test_bit_count
make DEBUG=1 run-test TEST=test_bit_count
make SANITIZE=1 run-test TEST=test_bit_count
make test-unit                   # все C-тесты без сборки CLI
```

### 3. Сделайте запускаемым (необязательно)

Добавьте `examples/bit_count.c` с конечным неинтерактивным `main`, который вызывает общий API и печатает результат. Добавьте `bit_count` в `EXAMPLE_NAMES` в `mk/examples.mk` и опишите его в `examples/README.md`. Этот явный список разрешённых примеров не допускает небезопасные исторические программы в обычные сборки; не используйте глоб-шаблон по всем примерам. Другие правила сборки не нужны, даже если пример использует общие алгоритмы.

```sh
make list-examples
make run-example EXAMPLE=bit_count
make test-examples
```

`tests/test_examples.py` уже проверяет код завершения, непустой вывод и 15-секундный тайм-аут для каждого перечисленного примера. При необходимости добавляйте туда проверки вывода, специфичного для алгоритма, и недопустимых аргументов; одни дымовые тесты не доказывают корректность. Если пример принимает аргументы, валидируйте их до сужения типов; переиспользуйте `cli_values.h` вместо `atoi` или непроверяемых преобразований.

Если опция CLI основного приложения полезна, добавьте её опцию/диспетчеризацию в `src/main.c`, валидируйте количество аргументов и числовой диапазон и расширьте `tests/test_cli.py` случаями успеха, границ, отсутствующих и недопустимых входных данных. Обновите `docs/usage.md`; добавляйте проверяемый сценарий в `demos/tour.py` только если это полезно. Держите парсинг и печать вне алгоритма.

### 4. Проверьте перед отправкой

```sh
make -j2 check                   # тесты C + CLI, поддерживаемые примеры, тур CLI
make sanitize                   # тесты C + CLI под ASan/UBSan
make CC=clang BUILD_DIR=build/clang BIN_DIR=bin/clang check
make docs                       # если установлен Doxygen
```

`make SANITIZE=1 check` также проверяет примеры и тур с инструментированием. Проверьте предупреждения компилятора, публичные контракты, эталонные/свойственные тесты и документацию. Если заявляете ускорение, проводите отдельный бенчмарк с теми же входными данными/компилятором/флагами, используйте результаты, чтобы воспрепятствовать удалению мёртвого кода, и сообщайте о компромиссах и границах погрешности. Более короткое выражение не обязательно быстрее или переносимее.

## Ограничения API

- Приближённые математические процедуры — это эксперименты, а не замена libm. Битовые приближения степени предполагают IEEE-754; `fast_pow` дополнительно предполагает little-endian представление `double`. Используйте положительные конечные входные значения в продемонстрированном диапазоне. Приближённые степени возвращают NaN для недопустимых входных данных или неподдерживаемых битовых диапазонов.
- `binary_pow` принимает беззнаковый целый показатель степени; дробные показатели не поддерживаются. `fibonacci` помещается в `uint64_t` только до индекса 93.
- API преобразования Фибоначчи документируют диапазон 0–100000 миль. Они приближают расстояния, а не выполняют точное преобразование единиц.
- `fast_mod` требует ненулевой модуль, являющийся степенью двойки. `next_power_of_two` возвращает ноль для нуля или переполнения выше 2^31.
- ГПСЧ не являются криптографически стойкими. Xorshift требует ненулевое зерно; API, использующие глобальное состояние, не потокобезопасны. `sha1_prng` требует 16 слов состояния.
- `is_palindrome_bit` проверяет, можно ли переставить строчные ASCII-буквы так, чтобы получился палиндром, а не является ли строка палиндромом уже. Другие символы возвращают false.
- Устаревший формат RLE не может представлять литеральные цифры. `rle_encode` требует входные данные без цифр и буфер размером не менее `strlen(input) * 3 + 1` байт. `rle_decode` выделяет точный размер развёрнутых данных; освобождайте результат. Недопустимые счётчики, арифметическое переполнение или сбой выделения памяти возвращают NULL. Для недоверенных входных данных используйте `rle_decode_limit`: он отвергает вывод сверх выбранного предела до выделения памяти. CLI использует предел 1 MiB; устаревший неограниченный API остаётся доступным.
- `fletcher32_string` использует 16-битные слова little-endian, дополняя нулём последний нечётный байт. `fletcher32` принимает количество слов, а не байтов.
- `levenshtein` возвращает -1 при сбое выделения памяти или неподдерживаемой длине входных данных. Если не указано иное, указатели должны быть допустимыми и не NULL.

Время бенчмарков зависит от компилятора и машины. Набор носит образовательный характер, а не является статистически контролируемым сравнением производительности; даже наблюдаемый результат не исключает полностью свёртывание констант и оптимизации.

## Документация и GitHub Pages

`Doxyfile` генерирует HTML из публичных заголовков, исходного кода, README и этого руководства. Он также включает сборник рецептов CLI, каталог/исходники примеров и руководство по демонстрациям. `docs/theme.css` накладывает локальный адаптивный стиль поверх Doxygen, включая тёмные цвета, удобочитаемые блоки кода и контуры фокуса клавиатуры. Навигация и поиск используют встроенные ресурсы Doxygen; во время CI удалённая тема не загружается. Рабочий процесс документации собирается на pull request и публикует только при push в `main` или при ручном запуске на `main`. Чтобы включить развёртывание в GitHub:

1. Откройте **Settings → Pages → Build and deployment**.
2. Выберите **GitHub Actions** как источник.
3. Отправьте изменения в `main` или запустите рабочий процесс **Documentation** вручную.

Среда `github-pages` может требовать одобрения, если этого требуют правила защиты репозитория. Задание развёртывания сообщает фактический опубликованный URL.
